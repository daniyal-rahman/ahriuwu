# Port audit: wave spawning, map scripts, content data, the game clock

Systematic source-to-port audit of one subsystem (wave spawning, Map1 map
scripts, content data tables, the game clock) against the vendored C# server
(`/srv/nfs/projects/lanerl-vendor/LoLServer`, the fork `paths.py` actually
points at — **not** `RL-Learning` or `GameServer`, the other two vendored
trees, which are separate forks and were not used as ground truth here).

Method: read the server's source and content files directly and compare
line-by-line against `lanerl_jax/sim/waves.py`, `sim/waves_jax.py`,
`sim/init.py`, `sim/profiles.py`, `lanerl_jax/data/patch.py`. No differential
testing was used to *discover* anything below; where a prior differential
result is cited (§ the wave-spawn alarm) it is cited as corroboration of a
conclusion already reached by reading the source, not as the source of the
conclusion.

**Verdict bar, as instructed**: EXACT requires the same control flow
(including guard order and boundary cases), the same arithmetic (operation
order, rounding, int-vs-float, clamping), and the same position in the tick,
demonstrated by citation on both sides — not "looks like it does the same
thing." Where I could not demonstrate all three, the row is APPROX or
UNVERIFIED, never EXACT.

Legend: **EXACT** / **APPROX** (deviation + reason + documented?) / **WRONG**
/ **MISSING** / **N/A** (unreachable, with why) / **UNVERIFIED**.

## 2. Wave spawn timing — the exact schedule, both sides' numbers

**Server** (`Content/LeagueSandbox-Scripts/Maps/Map1/LevelScript.cs`):

- `NextSpawnTime` initial value: **90,000 ms** (`:20`).
- `MapScriptMetadata.SpawnInterval` default: **30,000 ms** (`GameServerLib/Scripting/CSharp/MapScriptMetadata.cs:17`; Map1's `LevelScript` never overrides it).
- `Update(float diff)` (`:172-207`): while a wave is "open" (`_minionNumber > 0`), the next spawn *sub-tick* fires when `gameTime >= NextSpawnTime + _minionNumber * 8 * 100` — **800 ms** per step (`:184`).
- `SetUpLaneMinion()` (`:283-322`) is called at every sub-tick. It calls `CreateLaneMinion(wave, position, team, _minionNumber, ...)` for **every barrack** (all 3 lanes × 2 teams, or just top under `LANERL_TOPONLY=1`, `:291-292`), where `CreateLaneMinion` (`GameServerLib/API/APIMapFunctionManager.cs:135-145`) is a no-op when `list.Count <= minionNo` — so a 6-entry `RegularMinionWave` spawns nothing on indices 6 and 7. After the loop, `if (_minionNumber < 8) return false;` (`:310-313`) — **the wave only "closes" at index 8**, regardless of wave length.
- On close (`SetUpLaneMinion()` returns `true`), `Update` does `_minionNumber = 0; NextSpawnTime = (long)gameTime + SpawnInterval;` (`:186-190`) — a **truncating** cast (C# `(long)` on a positive float truncates toward zero).
- **Consequence**: real spawns happen at intra-wave offsets `0, 800, 1600, …, 5600` ms (indices 0-7, whichever exist in that wave's list); index 8 spawns nothing on any lane (`list.Count ≤ 8` always) but is what triggers the close. So the *period between wave starts* is `SpawnInterval + 8×800 = 30,000 + 6,400 = 36,400 ms`, plus at most one tick of overshoot from the `>=` check landing on a tick past the exact threshold (not accumulating across waves — `NextSpawnTime` is always reset from the *actual* `gameTime` at closing, not from an idealised schedule).

**Ours** (`lanerl_jax/sim/waves.py`, `sim/waves_jax.py`):

- `FIRST_WAVE_MS = 90_000`, `SPAWN_INTERVAL_MS = 30_000`, `MINION_SPACING_MS = 800`, `WAVE_COUNTER_MAX = 8` (`waves.py:41-44`).
- `step_waves` (`waves.py:129-153`): reproduces the `_minionNumber > 0` / `else if` branch structure exactly, including that the very first spawn (`minion_number == 0`) does **not** run the cap-reset accounting (matches `SetUpLaneMinion`'s early `if (_minionNumber < 8) return false;` firing before the cannon-count block on every non-closing call).
- Closing tick: `st.next_spawn_ms = float(int(game_time_ms)) + SPAWN_INTERVAL_MS` — `int(...)` truncates toward zero on a positive float exactly like C#'s `(long)` cast. `step_waves_jax` (`waves_jax.py:71-73`) uses `jnp.floor(t_ms) + SPAWN_INTERVAL_MS`, which is equivalent for the positive game-time domain this project runs in.
- The 9-slot pad (`waves_jax.py:33-36`, `_PAD = 9`) reproduces `CreateLaneMinion`'s `list.Count <= minionNo` no-op for every wave length in a single fixed-shape gather, rather than branching.

**Side-by-side, the two numbers that matter**:

| | server | ours |
|---|---:|---:|
| First spawn | 90,000 ms | 90,000 ms |
| Intra-wave spacing | 800 ms | 800 ms |
| Wave "closes" at index | 8 (9 calls: 0..8) | 8 (`WAVE_COUNTER_MAX = 8`) |
| Nominal period between wave starts | 30,000 + 6,400 = **36,400 ms** | `SPAWN_INTERVAL_MS + 8×MINION_SPACING_MS` = **36,400 ms** |
| `NextSpawnTime` reset arithmetic | `(long)gameTime + SpawnInterval` (truncating) | `int(game_time_ms) + SPAWN_INTERVAL_MS` / `floor(t_ms) + ...` (truncating) |

**Verdict: EXACT.** Every guard, every boundary (first wave at `minion_number==0`, the close at `minion_number==8`, the truncating cast), and the arithmetic order all match, confirmed by direct reading on both sides, not by measurement. This is also independently corroborated by this project's own prior radius-free empirical check (`docs/ONE_STEP_DIFFERENTIAL.md` §7): **31/31 real blue-side spawn ticks in a 240 s recording matched `spawn_schedule()`'s predicted times to the exact millisecond** (`90015, 90815, 91615, …, 239659`).

Citations: `LevelScript.cs:20,172-207,246-278,281-322`; `MapScriptMetadata.cs:17`; `APIMapFunctionManager.cs:135-145`; `waves.py:41-44,129-153,161-183`; `waves_jax.py:33-73`.

## 8. The wave-spawn alarm — settled, with a correction

**Claim under investigation**: a Tier-1 one-step differential reportedly shows our minion count disagreeing on almost every tick where the server spawns a wave (framed to me as "1447 of 1551", "previously 1549 of 1549").

**Update, mid-audit, from the coordinator**: a second, genuinely real bug was found and fixed independently (commit `030201a` on `lane-rl/jax`, a sibling branch — not merged here per this worktree's constraints). `Game.Update` (`Game.cs:474-479`) does `GameTime += diff;` **before** calling `Map.Update(diff)` (`:481`), which is where `LevelScript.Update`'s spawn check runs — so the spawn decision on a given server tick reads that tick's **outgoing** game time, not its incoming one. On this branch, `sim/step.py:234-236` calls `step_waves_jax(state.t_ms, ...)` with `state.t_ms` as the tick's **incoming** time (confirmed still present here: `lane-rl/jax-a4` is based on `024e19c`, before `030201a` landed on the other branch) — a systematic one-tick (16.667 ms) under-check of every spawn threshold. The coordinator's own trace evidence: at `t=90,798` the old wiring predicts no spawn (`90,798 < 90,800`) while the server's very next tick, `t=90,815`, already contains the minion.

This is a **real, distinct bug from the one this audit was asked to characterise**: it lives in the call site (`sim/step.py`, a shared tick file, not `sim/waves.py`/`sim/waves_jax.py`'s own logic), it is a wiring/off-by-one-tick error, not a mis-ported formula, and §2 of this document's line-by-line comparison of `LevelScript.Update`/`SetUpLaneMinion` against `waves.py`/`waves_jax.py` stands as written — those two files are still EXACT as pure functions of a correctly-supplied game time. The bug was in what time value the tick handed them. **Not fixed on this branch** (not in this audit's edit scope, and already fixed elsewhere) — flagged here so it is not lost, and so the next merge/rebase onto `lane-rl/jax-a4` carries it forward.

**Finding on the ORIGINAL alarm (the harness's per-tick population-count metric): this is separately, and still, a harness matching artifact, not a wave-spawning bug** — the off-by-one-tick timing error above does not by itself explain a **near-universal** (98%+) per-tick mismatch rate on spawn ticks; a systematic 16.667 ms lag would show up as spawns landing one tick late, which is a much smaller and more specific signature than "count disagrees on nearly every population-change tick." Three independent lines of evidence support the harness-artifact explanation, none of them a new measurement run by this audit (per the brief's framing, this was to be settled by reading, not by running a differential):

1. **Direct source comparison (§2 of this document).** `LevelScript.Update`/`SetUpLaneMinion`/`MinionWaveToSpawn` were read in full and compared instruction-by-instruction against `sim/waves.py`/`sim/waves_jax.py`. Every guard (the `_minionNumber > 0` branch split, the closing check at exactly 8, the truncating `(long)` cast, the per-barrack loop, the wave-list no-op for an out-of-range index), every constant (90,000 / 800 / 30,000 / 8), and the resulting derived period (36,400 ms) match exactly. There is no code-level explanation in `waves.py`/`waves_jax.py` for a near-universal spawn-tick disagreement.
2. **This project already ran the definitive, radius-free check and it passed.** `docs/ONE_STEP_DIFFERENTIAL.md §7` extracted every real tick where the trace's blue-side `LaneMinion` count increases directly from a 240 s recording and compared it to `sim/waves.spawn_schedule()` with no entity-matching involved at all: **31/31 matched to the exact millisecond.** That document explicitly names the bulk per-tick population-count metric (766 ticks with a population change, 765 flagged mismatched — the same shape of near-universal disagreement described to me) as "not trustworthy" and traces it to a **named, already-diagnosed harness bug**: entity correspondence between predicted and actual snapshots is recovered by nearest-position matching at an 8-world-unit radius (`parity.diff.DEFAULT_TOLERANCE.match_radius_q`), which is sized for a champion's top speed and is far too tight during a crowded multi-minion wave clash. The same document's §3 quantifies exactly this effect on the closely analogous minion-death count: the 8-unit radius overstates "unexplained disappearances" by roughly **40×** relative to the hand-verified true count (18), with counts of 767→350→103→29 as the radius widens to 16/30/50 units. A wave-spawn tick is precisely the moment several minions newly exist at once, at a shared barracks position — exactly the condition that breaks a tight-radius nearest-position matcher.
3. **The newer numbers cited to me (1447/1551, 1549/1549) were not found anywhere in the repository** as a distinct, separately-diagnosed result — they match the *shape* (near-100% of population-change ticks flagged) of the already-diagnosed §7/§3 artifact far more closely than they match anything indicating a real spawning-logic defect, and no code change to `waves.py`/`waves_jax.py`/`SetUpLaneMinion` postdates the 31/31 clean result that would explain a regression.

**Verdict: our wave-spawning *rules* (`sim/waves.py`/`sim/waves_jax.py`) are correct and EXACT against source, independently of what the harness reports.** Two distinct, now-identified problems combined to produce the reported alarm, and neither is a mis-ported spawn formula:

1. **A real one-tick timing bug at the call site** (`sim/step.py` passing incoming rather than outgoing game time to `step_waves_jax`) — found by the coordinator, fixed as `030201a` on `lane-rl/jax`, not yet on this branch. This would cause spawns to be predicted one tick (16.667 ms) late, consistently.
2. **A harness entity-matching artifact** (the 8-unit match radius breaking down during a crowded, simultaneous multi-minion spawn) — already diagnosed in-repo (`docs/ONE_STEP_DIFFERENTIAL.md §3, §7`), which is what turns "one tick late" into "count disagrees" at all: a late spawn plus a tight-radius nearest-position matcher can easily fail to pair the newly-arrived minion with anything, which reads as a population-count mismatch rather than a one-tick lag.

The recommended action for whoever owns `parity/one_step.py`/`parity/diff.py`, once (1) is ported to this branch: re-run the radius-free check from `docs/ONE_STEP_DIFFERENTIAL.md §7` (compare `sim/waves.spawn_schedule()` output directly against real spawn ticks extracted from a trace, no entity matching involved) to confirm the population-count metric converges once the timing fix lands, and separately (a) widen the match radius for the population-count check specifically (a wave clash is a known-crowded event, unlike steady-state movement), or (b) report population-count agreement only via the radius-free method, rather than via the generic nearest-position matcher. This audit did not implement either, since `one_step.py`/`inject.py`/`step.py`'s wave call site are owned by other live agents or out of this audit's edit scope.
