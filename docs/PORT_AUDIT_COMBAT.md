# Port audit: stats, damage, buffs, spells, missiles, death/gold/XP

Source-to-port audit of the combat subsystem, done by reading the vendored C#
server exhaustively and comparing it line-by-line against `lanerl_jax`. This is
**not** a differential-testing report — every row below is backed by a file:line
citation on both sides (or an explicit reachability argument for N/A). Where a
claim could not be nailed down to that standard, it is marked UNVERIFIED rather
than guessed into EXACT.

## Ground truth and methodology corrections

- **Vendor root used**: `/srv/nfs/projects/lanerl-vendor/LoLServer` — confirmed
  byte-for-byte identical to `/srv/nfs/projects/lanerl-vendor/GameServer`
  (`diff` of `Stats.cs` between the two: 0 lines) and the tree that matches the
  compiled `GameServerConsole` binary per `lanerl_train/paths.py:server_dir`.
  `/srv/nfs/projects/lanerl-vendor/RL-Learning` is a **different, stale fork**
  (380-line diff on `Stats.cs` alone) and was not used for any citation below.
- This is a **custom fork of LeagueSandbox** with an added
  `GameServerLib/Lanerl/` directory (`LanerlEpisode.cs`, `LanerlHooks.cs`,
  `LanerlControl.cs`, `LanerlBot.cs`, `LanerlConfig.cs`, `LanerlAim.cs`,
  `LanerlFow.cs`, `LanerlLane.cs`, `LanerlStateDump.cs`, `LanerlWire.cs`, ~5000
  lines) written for this RL project. `LanerlAim.cs` in particular is a
  hand-written **reimplementation** of autoattack timing/damage for bot-AI
  heuristics — it is informative but was **not** treated as ground truth
  anywhere below; every claim sourced from it was cross-checked against the
  real engine file (`Stats.cs`, `ObjAIBase.cs`, `Spell.cs`) it claims to mirror.
- **Minion model names**: an early pass in this audit almost cited `SRU_*`
  character folders (`SRU_OrderMinionMelee`, `SRU_ChaosMinionSiege`, ...) for
  minion `UnitTags`. Those are very likely **not** what Map1 spawns — Map1's
  actual minion spawn table is `Content/LeagueSandbox-Scripts/Maps/Map1/
  LevelScript.cs:27-36`, which names `Blue_Minion_Basic` / `Red_Minion_Basic`
  (melee+caster share this model), `Blue_Minion_MechCannon` /
  `Red_Minion_MechCannon` (siege/cannon), `Blue_Minion_MechMelee` /
  `Red_Minion_MechMelee` (super). `lanerl_jax/data/patch.py`'s `MINION_MODELS`
  table already uses the correct names. The `UnitTags` string is identical
  between the `SRU_*` files and the real Map1 models (verified both), so no
  finding below changed as a result, but citations were corrected to the real
  files. **Lesson reproduced from the brief, not just repeated**: always
  confirm which character-named file the running map actually loads before
  citing it.
- **A systemic pattern found this session, load-bearing for several rows
  below**: several `GlobalCharacterDataConstants`/`ChampionVariables`/
  `ObjAIBaseVariables` fields are declared, loaded from each map's
  `Constants.json` (`GameServerLib/Content/GlobalData/GlobalData.cs:26-99`),
  and then **never read by any gameplay code** — confirmed by exhaustive
  `grep` for the exact field name across `GameServerLib` and `Content` for each
  one individually. Confirmed dead: `DamageRatios` (all 9 fields —
  `dr_UnitToHero=0.6`, `dr_BuildingToUnit=1.25`, `dr_UnitToBuilding=0.5` on
  Map1, meaning "creeps deal less damage to champions" / "turrets deal more to
  creeps" is **configured but never enforced**), `GoldRadius2`,
  `MinionEXPMods`, and (separately confirmed, lower-confidence — no explicit
  clamp call site found in `Spell.cs`/`Stats.cs`, but not as exhaustively
  grepped as the first three) `AttackMinDelay`/`AttackMaxDelay`/
  `PercentAttackSpeedModMinimum`/`PercentCooldownModMinimum`. Anywhere a row
  below says a mechanic is "EXACT-by-bug-compat" for **not** implementing one
  of these, this is why: our port's omission matches the server's own
  non-enforcement, and *adding* the mechanic later would be the actual
  divergence.
- Tick order, confirmed directly from `AttackableUnit.cs:237-271`
  (`Update`): `UpdateBuffs(diff)` → stat-tick accumulator (`Stats.Update`,
  gated `_statUpdateTimer >= 500`) → `Replication.Update()` → movement
  (`CanMove()`/`DashMove`). `Die()`/AI/targeting/autoattack-cooldown follow in
  `ObjAIBase`'s override, per the brief's own ground-truth note, not
  re-verified line-by-line here beyond the shared `AttackableUnit` base. Our
  `sim/step.py` runs buffs → regen → movement → targeting/AI → autoattack/
  missile resolution → alive/died transition → respawn, all vectorized in one
  pass per tick rather than a serial per-object loop — see the dedicated
  ordering row under "AttackableUnit: damage, death, shields" for why this is
  an accepted structural approximation, not a bug.

## Cross-check against a parallel audit pass

A separate audit pass of this same subsystem was committed to this branch
(`93b1296`, authored during this same session) while this revision was being
written. Its conclusions were read in full and compared row-by-row against
this document's findings. **The two passes independently converge on every
major finding** — the W-active damage-reduction server bug, the UnitTag/
super-minion passive-interrupt bug (including the missing level-11
re-exemption), the champion-kill gold/XP omission, the turret-ramp formulas,
the missile launch-vs-hit AD snapshot, and the Q-empowered-attack missing
hook were all found by both passes independently, which is strong evidence
none of them is a fluke of one session's framing. Differences worth naming
explicitly:

- **Minion `UnitTags` citation**: both passes' first draft cited the
  Map11-only `SRU_*` character folders for minion `UnitTags`; this pass
  additionally traced Map1's actual spawn table
  (`Content/LeagueSandbox-Scripts/Maps/Map1/LevelScript.cs:27-36`) and
  confirmed the real Map1 models (`Blue_Minion_Basic`, `Blue_Minion_MechCannon`,
  `Blue_Minion_MechMelee`, and Red equivalents) carry byte-identical
  `UnitTags` strings — so the conclusion is unchanged, but the citation in
  this document is to the file the server actually loads, not a same-named
  but wrong-map one.
- **W passive's Armor/MR mechanism — a genuine disagreement, resolved by
  arithmetic.** The other pass reads `Armor.PercentBonus += 0.2;
  Armor.PercentBaseBonus -= 0.2;` as "a specific idiom" that nets out to a
  clean +20% and scores the row **EXACT**. Multiplying out `Stat.Total`
  shows this is not so: with no other percent modifiers active,
  `Total_after = (0.8*(BaseValue+BaseBonus) + FlatBonus) * 1.2`. For
  `FlatBonus=0` (Garen's MagicResist, no item/rune MR bonus in this config)
  that is `0.96 * Total_before` — a **4% decrease**, not +20% — and for
  `FlatBonus=9.0` (Garen's measured rune Armor delta) it is a small,
  level-dependent net that goes *negative* by roughly level 11 as base
  Armor outgrows the fixed flat term. This is the exact "clamping/ordering
  placement changes the answer" trap the coordinator warned about, just one
  algebra step further in: a plausible-sounding idiom description is not a
  substitute for multiplying out the formula. This document's own §6 table
  shows the full derivation; it is scored **WRONG**, not EXACT, and is
  independently reproduced by both of this session's own audit slices that
  looked at it, one of which was specifically alerted to double-check the
  other's finding before agreeing.
- **Champion-kill gold/XP formula**: the other pass located and transcribed
  the exact live formula from `Champion.cs:392-461` (`Champion.Die`) in more
  numeric detail than this pass's own first read — the kill-streak
  multiplier `(7/6)^(KillSpree-1)` capped at `ChampionMaxGoldValue`, a
  death-spree discount (`gold *= 11/12`, then `Math.Max(gold*0.8^(DeathSpree/2),
  ChampionMinGoldValue)` for repeat deaths), and first-blood's flat addition.
  Re-verified directly against `Champion.cs:392-450` in this pass too (exact
  line numbers below); both passes agree once transcribed at this level of
  detail. One addition from this pass: `Champion.Die` will still credit gold
  to whichever enemy champion most recently damaged the victim
  (`_championHitFlagTimer`/`_playerHitId`, `Champion.cs:404-408`, comment:
  `"Killed by turret, minion or monster, but still give gold to the enemy"`)
  even when the killing blow came from a turret/minion/monster — so
  "champion kill gold" is really "died-while-recently-hit-by-an-enemy-
  champion gold," a slightly broader trigger condition than "landed the
  killing blow."
- **Autoattack windup/cooldown clock (§5 here)**: the other pass explicitly
  left this section as a pending placeholder (its own §7 note: "pending
  sub-audit results — to be merged in on completion"), so its committed
  version does not cover the cooldown gate-vs-decrement ordering bug or the
  champion attack-speed-frozen bug this document's §5 documents in full —
  those two rows (this document's priority-list items 1 and 5) are unique
  contributions of this pass, not corroborated by a second independent read.
  Treat them with correspondingly one notch less certainty than the
  triple/double-confirmed rows above, though each has a direct file:line
  citation and worked arithmetic behind it.
  - **Update: the "gate-vs-decrement" row (§5's first row, priority-list
    item 5) is the second independent read this section called for, and it
    does not corroborate — it refutes.** The literal code-order difference
    is real (server checks the swing gate before decrementing; ours
    decrements before checking), but it was never actually simulated before
    being scored WRONG. A discrete-time recurrence, checked by hand and then
    confirmed with a 2000-trial randomized simulation (periods 200-3000ms,
    both orderings, seeded from every reset value either side's own code can
    actually produce — `0` and a freshly-set `attack_period`), shows the two
    orderings fire on the identical tick index every time, with zero drift
    across 600+ ticks. The row has been corrected to EXACT in §5 below, with
    the full derivation inline. **The champion attack-speed-frozen finding
    (priority-list item 1) is unaffected by this correction** — that one
    does not depend on decrement ordering at all (it is a level-scaling
    omission in `profiles.py`/`step.py`, verified independently in this
    session's other document too) and stands as scored.
- **The `DamageRatios`/`GoldRadius2` "declared but dead" constant pattern**
  (this document's methodology note above) was not found by the other pass,
  which instead found `MinionEXPMods` as its one example of the same
  pattern. Both are real; neither pass found the other's instance, which is
  itself a useful data point about how easy this class of bug is to miss —
  worth grep-checking any other `Global*.cs` constant class the same way
  before trusting a declared value is enforced.

## Verdict legend

**EXACT** — control flow, arithmetic (including rounding/operation order), and
tick ordering all independently verified to match. **APPROX** — same shape,
documented deviation, with a note on what would make it EXACT and whether that
fix is JAX-hostile. **WRONG** — verified divergence with real behavioral
effect. **MISSING** — server mechanic with no port equivalent at all.
**N/A** — mechanic confirmed unreachable in this project's config (Garen vs
Garen, 1v1, top lane, Map1, no items unless noted), with the reachability
argument given inline. **BUG-COMPAT** — the server's behavior is a bug and the
row records whether we reproduce it. **UNVERIFIED** — could not be nailed down
to the EXACT bar in the time available; flagged rather than guessed.

This is **the same bug, in a sibling stat**, that this audit was explicitly asked to check for after finding it in attack damage — confirmed present, unfixed. It grows monotonically all game and affects DPS, farming speed, and every last-hit window from mid-game on.
2. **Garen's W active damage reduction never reaches health on the real server, but does in our sim** (§2, §6 — triple-confirmed by three independent readings of `AttackableUnit.cs:551-618` and `GarenW.cs`, all agreeing on exact line numbers). A verified value-type/reference ordering bug in the vendored server means W's "0.7x incoming damage" never touches `Stats.CurrentHealth`, only a cosmetic damage-number packet. Our sim implements the real, intended 30% reduction instead. Asymmetric per W-timing; large, direct effect on every trade or dive where W is up.
3. **Garen's W passive Armor/MR bonus is computed backwards** (§6): the server's `PercentBonus += 0.2; PercentBaseBonus -= 0.2` compounds to a **4% MR decrease** (not +20%) in this itemless config, and a small, level-dependent Armor effect that goes *negative* past ~level 11 — the opposite of our sim's flat `*1.2` on both stats. Unlike the active-window bug above, this is **always on** from the moment W is first ranked (level 3+), so it biases nearly all damage math for the rest of the game, not just active-window trades. Ranked just below the active-window bug only because its per-hit magnitude is smaller; in aggregate exposure (uptime) it is arguably more consequential.
4. **Champion-kill gold and XP are entirely unmodeled** (§4). In a Garen-vs-Garen 1v1, killing the enemy champion is the single highest-value discrete in-lane event and currently returns 0 gold, 0 XP, with no kill-streak/first-blood/level-catch-up state (`KillSpree`/`DeathSpree`/`Assists` don't exist in `state.py`). Directly distorts any reward or economy signal downstream of a champion kill.
5. ~~Autoattack cooldown clock: gate-then-decrement vs. decrement-then-gate ordering is reversed~~ — **RETRACTED, corrected to EXACT.** The code-order difference is real but does not change which tick a swing fires on; see §5's first row and the "Cross-check" section above for the simulation that refutes this item. Left struck-through rather than deleted so the correction is visible in place, per this document's own "commit the mistake and the fix" pattern elsewhere.
6. **The passive's out-of-combat combat-interrupt rule is wrong for both siege and super minions** (§1, §6 — independently confirmed by two slices): super minions are treated as never interrupting Garen's passive (they should, below level 11, identically to cannon minions), and neither minion type's interruption is turned back off at level 11+ as the server does. Changes exactly how much sustain Garen gets while farming near cannon/super waves, level-dependently.
7. **Missing `CancelAutoAttack`/target-death-mid-windup handling, and `HasMadeInitialAttack`** (§5): a target that dies or leaves range mid-windup should abort the swing and free the cooldown immediately on the server; our sim runs the windup to completion on its original schedule regardless. This directly corrupts contested last-hits (a minion dying to something else mid-swing) and post-trade re-engagement timing — precisely the CS-accuracy axis this project cares about most, even though its aggregate magnitude is likely smaller than items 1-3.
8. **Turret/inhibitor kills pay no gold or XP to anyone** (§4). Rarer than minion CS in a short episode, but a real, non-trivial gold/XP spike (150-175 local/global gold, 100 global XP) that vanishes silently; the turret profile data itself is architecturally wrong (parses Content fields that are always 0 for turrets, never the `Local`/`Global`-prefixed ones actually used), not just unwired.
9. **Garen R's cast-to-hit windup (~0.435s) is collapsed to instant** (§3): both the execute damage snapshot and the cooldown start happen early relative to the server — can flip close-timing kill/trade outcomes right at the moment R is used to finish a target. Q/W/E are correctly instant (confirmed via each ability's `InstantCast` flag bit) — this is isolated to R.
10. **Q's empowered-attack bonus damage and silence have no attachment point in the live pipeline** (§5, §6): the formulas exist and are correct (cross-checked against Content JSON) but are called from nowhere except tests. Already self-documented honestly in `spells.py`. Narrows Q's value as a poke/last-hit/silence tool without corrupting baseline auto-attack math.
11. **Magic resist is not grown by level** (§1) — the same class of omission as the AD/attack-speed bugs above, flagged but not independently confirmed with the same rigor. Likely small in an all-physical Garen mirror, which is probably why it was missed originally; worth the same fix treatment regardless.
12. Lower-severity / narrower items, roughly in descending order: missile launch-vs-hit AD snapshot for ranged autoattacks (§5, currently a provable no-op given this project's unit roster, but not literally correct); R's mitigation reading raw rather than W-passive-adjusted MR (§6, minor, compounds item 3); E's ~500ms tick-phase offset from the server's pre-loaded timer (§6, small timing shift, similar total damage); W's Tenacity bonus magnitude bug in the server itself, 30 vs. 0.30 (§6, currently inert on both sides — nothing in this matchup applies CC to Garen or reads Tenacity); CDR mechanism entirely absent (§3, plausibly always-0 in this config but not proven); the `AttackDamagePerLevel.RemoveStatModifier` asymmetry bug in the server itself (§1, confirmed unreachable given how masteries are applied in this project).

## Design decisions for the human

- **Buff engine architecture** (§1): reproducing each buff's effect functionally rather than building a generic `Buff`/`StatsModifier` object system is a reasonable, deliberate trade for a fixed, small, fully-enumerated kit (Garen only), but does not scale to additional champions/items without re-deriving each one by hand from source, the way this whole audit had to. Not JAX-hostile to keep as-is for the current project scope; would become the limiting factor the moment a second champion or a real item build is added.
- **Rune/mastery page as measured deltas rather than reconstructed stats** (§1, §4): already a considered, documented decision from a prior session (`sim/init.py`'s `RUNE_HP_BONUS`/`RUNE_AD_BONUS`/`RUNE_ARMOR_BONUS`), correctly avoiding a previously-burned approach (reconstructing specific runes got AD wrong three times). This audit did not re-derive it, but flags that it covers HP/AD/armor only — MR, mana, regen, movespeed, and any gold/XP-modifying rune/mastery stats are unmeasured and unmodeled. Extending the same measurement method to those stats is the natural next step if any of them turn out to matter.
- **Items 1, 2, 3, 5, 6, 7, 9, 10 above are all independent, mechanical bugs with clear fixes** (not architecture trade-offs) — each has a precise citation on both sides and a well-defined "what would make it EXACT." None are JAX-hostile: they are ordinary control-flow/arithmetic corrections (re-derive attack-speed live from level the way attack damage already is; fix the W-active damage-multiplier application order or, for bug-compat, remove it entirely; fix the W-passive formula to the real compounding arithmetic; add a champion-kill gold/XP path; fix the gate/decrement order in the cooldown clock; add the super-minion case and the level-11 re-exemption to the passive interrupt; add a target-validity check to the windup/swing-completion path; give R a real windup state; wire `q_damage_at_rank`/`q_silence_duration_at_rank` into a landing-swing hook). The one genuinely architectural question is whether to invest in a generic per-swing damage-modifier/event-hook system (needed for both Q's empowerment and, properly, `CancelAutoAttack`) versus continuing to hand-thread special cases through `step.py` — that trade-off is the one item on this list worth a design conversation rather than a straightforward bug fix.
