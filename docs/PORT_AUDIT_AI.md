# Port audit: unit AI, orders, and target acquisition

Scope: `ObjAIBase`/`Champion`/`LaneMinion`/`Minion`/`BaseTurret`/`LaneTurret`,
`LaneMinionAI`/`TurretAI`/`MinionAI`, `ClassifyUnit`, order handling
(`OrderType`, `UpdateMoveOrder`, `LanerlControl`), and the call-for-help
dispatch path, against `lanerl_jax/sim/targeting.py`, `sim/minion_ai.py`,
`sim/orders.py`, `sim/autoattack.py`, and the AI/targeting portions of
`sim/step.py`.

Server tree read: `/srv/nfs/projects/lanerl-vendor/LoLServer` (the tree that
actually builds `GameServerConsole` — confirmed against
`lanerl_train.paths.server_binary()`; `GameServer/` and `RL-Learning/` are
stale sibling copies with diverging content and were **not** used for any
citation below). All server-side line numbers are absolute lines in that
tree. Ours: `/srv/nfs/projects/ahriuwu-lanerl-jax-a1`, `HEAD=024e19c`.

**Verdict legend.** EXACT = demonstrated equivalent control flow, arithmetic,
and tick ordering (not "looks similar"). APPROX = deliberate, documented
deviation. WRONG = unintentional divergence. MISSING = not implemented.
**UNVERIFIED** = added to the legend for this pass, on the coordinator's
instruction: used where I could not chase a claim to a demonstrated
equivalence in the time available. An honest UNVERIFIED beats a wrongly-green
EXACT. N/A = server code path is provably unreachable in our configuration,
with the unreachability traced through actual registration/dependency code,
not asserted from a map name or from "nothing measured it happening."

This vendor tree is **not** stock LeagueSandbox. It carries this project's own
instrumentation (`LANERL_AGGRO_TRACE`, `docs/CALL_FOR_HELP_SWITCH_RATE.md`-style
comments already inside `LaneMinionAI.cs`) and a custom RL control plane
(`GameServerLib/Lanerl/*.cs`, ~5,000 lines) that previous sessions of this
project apparently added upstream. That control plane, not the packet handler
a human client uses, is the actual order-ingress path for our sim, and one of
the largest findings below comes directly from reading it.

## 3. Order ingress — `LanerlControl`, not `HandleMove` (**the load-bearing finding**)

Our headless training/eval/parity harness never goes through the normal
client packet path (`GameServerLib/Packets/PacketHandlers/HandleMove.cs`,
which *does* clear `TargetUnit` on a plain ground click by passing
`SetTargetUnit(u)` with `u = GetObjectById(req.TargetNetID)`, typically null).
It goes through `GameServerLib/Lanerl/LanerlControl.cs`, a ~500-line custom TCP
control-plane class this project added to the vendor tree, gated on
`LANERL_CONTROL_PORT`. `orders.py`'s own docstring already knows this file
exists and quotes it — but got one of its three actions backwards.

| # | mechanic | server (file:line) | ours (file:line) | verdict | evidence |
|---|---|---|---|---|---|
| 3.1 | `Attack` order: `SetTargetUnit` **alone**, no `UpdateMoveOrder` | `LanerlControl.cs:373-392` (`case LanerlOrderKind.Attack`, comment at :386-390 explains *why*: adding `UpdateMoveOrder(AttackTo)` "clobbers the target and the champion never swings") | `sim/orders.py:131,162-163` (`attacking = ... ; target=jnp.where(..., attacking, otgt, ...)`, `move_order` untouched by `attacking`) | EXACT | Confirmed both sides: neither touches `move_order`/`MoveOrder`. |
| 3.2 | `Move` order: paths and sets `MoveOrder=MoveTo` (`publish=false`) — **does not touch `TargetUnit` at all** | `LanerlControl.cs:349-371` (`case LanerlOrderKind.Move`; `champ.SetWaypoints(path)` then `champ.UpdateMoveOrder(OrderType.MoveTo, false)`, no `SetTargetUnit` call anywhere in the case) | `sim/orders.py:130,158-163` (`moving = ...`; `target=jnp.where(moving, jnp.int8(-1), ...)`) | **WRONG** | `orders.py`'s own comment (`:160`) asserts *"A move order CLEARS the target: the server's MoveTo replaces AttackTo…"* — this is false of the code path that actually drives our training/eval/parity harness. `UpdateMoveOrder` itself only clears `TargetUnit` for `OrderNone`/`Stop`/`PetHardStop` (`ObjAIBase.cs:1353-1360`); `MoveTo` is not in that set. Corroborated independently by `LanerlBot.cs:1242-1251`: the scripted bot ships a dedicated `ClearTarget()` helper whose doc comment reads *"Drop the target so the engine stops swinging"* — a helper that would be pointless if `MoveTo` already did this — and `MoveTo()` (`LanerlBot.cs:1253-1301`) never calls it. **Practical consequence** (traced through row 2.3): a champion holding a valid target that receives a `Move` order does not disengage on the server — `RefreshWaypoints` (`ObjAIBase.cs:602-604`) flips `MoveOrder` back to `AttackTo` and re-paths *toward* the target the very next tick, for as long as the target stays alive and visible, regardless of distance (row 2.2). | 3.3 | `Recall`: `UpdateMoveOrder(Stop, publish=false)` before casting the pill | `LanerlControl.cs:471` | not modeled (Recall isn't in scope for this subsystem's files) | N/A | Out of AI/targeting scope; noted only because it's the third `publish=false` `UpdateMoveOrder` call and corroborates that our champion order plane should generally *not* run the `ApiEventManager.OnUnitUpdateMoveOrder` gate — irrelevant to a sim with no script listeners on that event, so inert either way. |
| 3.4 | Wire order-kind set is `{Noop, Move, Attack, Cast, Level, Recall}` — **there is no `Stop` order on this wire at all** | `GameServerLib/Lanerl/LanerlWire.cs:11-19` (`enum LanerlOrderKind`); `LanerlControl.cs`'s `switch` in `Execute` has no `Stop`/default case | `sim/orders.py:53-54` (`OrderKind.STOP = 3`), applied at `orders.py:132,166-169` | **MISSING** (wire-level) — flag for the human, not a bug in isolation | Whatever `OrderKind.STOP` is wired to in the action space (`lanerl_rl.constants`, out of this subsystem's file list) has no equivalent action the real `LanerlControl` server can ever receive. If the action space actually exposes a distinct "stop" button to the policy, that policy is being trained against an action the deployed/real-server harness cannot execute. This compounds with 3.2: since the real wire has no way to explicitly clear a target either, "stop" and "move-away" are *both* unavailable disengage tools on the real server once a target is set — worth deciding deliberately rather than each landing independently. |

`grep -rn apply_orders lanerl_jax/ lanerl_train/` confirms this is not a
theoretical path: `trainer.py:195`, `benchmark.py:117`, and every
`parity/*.py` harness call `apply_orders(state, orders)` once, then
`step_decision`/`tick` — the exact `apply-one-action, then-N-ticks` shape
`LanerlControl.OnTick` implements (`LanerlControl.cs:132-176`, gated by
`LANERL_STEP_TICKS`/`_stepTicks`).
